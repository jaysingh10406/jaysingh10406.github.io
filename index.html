Featured case study

Rebuilding an engineering foundation

I joined Future Energy Enterprises as Director of Software Engineering in October 2025. The company had no source control. Containers were mounted onto ECS by hand. The AWS account was controlled by an outside vendor, who also held roughly half the engineering work. Nobody could say with confidence what was running in production, or why it behaved the way it did.

When I inherit a system I look at custody first — who can change this, who can see it, who owns the account it runs in. Architecture review is worth very little while the answer is "someone else." Eleven months later the organization runs on infrastructure it controls, a release process it can repeat, and telemetry that tells it the truth.

What changed

Before

  • No source control
  • Manual container deploys
  • Vendor-held AWS account
  • No useful telemetry
  • Invocation counted as success
→

After

  • Git workflow, reviewed changes
  • Repeatable gated releases
  • Company-controlled infrastructure
  • Completion-aware monitoring
  • Documented engineering practice

Execution is not completion

The analysis kept arriving at one assumption buried in the application: invoking a background job was treated as evidence the work had succeeded. The success signal stopped two steps too early.

  1. 1 Job invoked
  2. 2 Worker started
  3. 3 Business operation
  4. 4 Verified completion

The old success signal stopped after step 2. Everything past it could fail without producing a signal.

Errors were swallowed. Workers failed silently. Underneath sat race conditions and database deadlocks. I rebuilt observability around verified completion rather than invocation, then fixed the failure modes that exposed. Failures started announcing themselves instead of being found later, by someone else.

Read the full sequence, eight stages

The order is the part I would want to be judged on. Each stage is a precondition for the next: you cannot run root cause analysis on a system you cannot see, you cannot safely change infrastructure without a pipeline, and you cannot have a pipeline without source control. Nobody handed me that sequence.

  1. 01

    Source control

    The organization had none. I established a Git workflow.

    Every change became reviewable, attributable, and reversible.

  2. 02

    Account custody

    The AWS account sat with an outside vendor. I brought it under direct company control.

    We could change our own infrastructure without asking permission.

  3. 03

    Audit of what we had inherited

    Catalogued outdated dependencies and misconfigurations across the codebase and infrastructure, including credential handling that belonged in AWS SSM and an unsafe deletion policy, then remediated them.

    A known starting state instead of an assumed one.

  4. 04

    Delivery

    Replaced manual container mounting with a CI/CD pipeline across dev, staging, and production. An outside vendor had quoted roughly 600 hours for the work; I judged that the number described the vendor's position rather than the problem, and built it in about a week.

    80+ deployments in three months. The pipeline is used, not just built.

  5. 05

    Security controls

    Led the engineering side of the company's first SOC 2 certification and the controls that sustain it: single sign-on, SAST, dependency scanning, and continuous vulnerability remediation, all built and run in-house.

    A security posture we could evidence rather than assert.

  6. 06

    Observability

    Instrumentation and alerting on a system that had neither, then structured root cause analysis on what it surfaced.

    Failures could be investigated with evidence instead of recollection.

  7. 07

    Execution is not completion

    Invoking a background job was treated as evidence the work had succeeded. Errors were swallowed, workers failed silently, and underneath sat race conditions and database deadlocks. I rebuilt observability around verified completion rather than invocation, then fixed the failure modes that exposed.

    Failures started announcing themselves instead of being found later, by someone else.

  8. 08

    The team can run all of the above without me.

Selected technical work

Small systems, built to reason through problems from the work above. The engineering decisions matter more than the stacks.

Webhook Inspector

FastAPI · WebSocket · React · asyncio

Generates a unique URL, captures any HTTP request sent to it, and streams it to the browser as it lands. Built for the job I actually reach for it on: debugging a customer's webhook integration when the payload is not what either side expected.

The design decision worth defending is the storage. Captured requests live in a bounded in-memory deque capped per bin, and there is no database. Debugging traffic is ephemeral by nature, so durability would have bought nothing and cost a schema, a migration path, and an operational dependency. The bound matters more than the persistence: without a cap, one noisy integration exhausts memory.

That choice has a clear expiry. Live push uses per-subscriber asyncio.Queue fan-out inside a single process, so the moment this runs on more than one worker, a request captured by one process will not reach a browser connected to another. That is where Redis pub/sub earns its place, and not before.

security-cicd-templates

GitHub Actions · AWS OIDC · Trivy · Bandit

Reusable workflow_call workflows for the pipeline shape I have now built twice: static analysis, dependency scanning, build, deploy. A consuming repository references them with a single uses: line instead of hand-rolling CI again.

Deployment authenticates to AWS through OIDC rather than long-lived access keys held in GitHub secrets. That removes a standing credential from every repository that deploys, which is the difference between a secret that can leak and a token that expires on its own. Dependency scanning uploads SARIF to GitHub code scanning so findings land where engineers already work rather than in a report nobody opens.
